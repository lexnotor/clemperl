# T6d, les litiges : plan d'exécution

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development
> (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps
> use checkbox (`- [ ]`) syntax for tracking.

**Goal :** un acheteur conteste une commande expédiée en désignant les articles et en
déposant ses preuves, le vendeur répond, l'administration tranche, et l'acheteur dit qu'il a
été servi.

**Architecture :** le litige est un objet à part, rattaché à la commande, qui garde son état
`SHIPPED`. Les règles sont pures dans `packages/domain` (éligibilité, transitions, maturité,
validation, courriels). Les écritures sont des comparaisons-et-échanges dans un dépôt neuf de
`packages/db`, et chaque lecture porte la portée de son lecteur dans sa signature. Les pièces
vont dans le bucket privé des justificatifs, servies par une route gardée dans chacune des
trois applications.

**Tech Stack :** Prisma 7.10 et PostgreSQL 17, Next.js 16 en server actions, next-intl 4
dans la boutique, Jest pour l'intégration dans `apps/api`, Vitest pour les tests unitaires,
Playwright pour le navigateur, Supabase Storage pour les pièces.

**Spec :** `docs/superpowers/specs/2026-10-19-t6d-litiges-design.md`

## Avant la tâche 1

- Les paquets sont rebâtis : `pnpm turbo run build --filter='./packages/*'`. Un `dist`
  périmé fait tomber des tests sans rapport, voir `docs/pieges.md`.

## Global Constraints

- Identifiants, noms de fichiers, segments d'URL et clés de traduction en **anglais** ;
  documentation, commentaires et libellés en **français**.
- Aucun tiret cadratin ni demi-cadratin nulle part, code et prose compris.
- Indentation : **4 espaces** en TypeScript, **2 espaces** dans les JSON du dossier
  `packages/i18n/messages/`.
- **Aucune configuration Prettier** dans ce dépôt : ne pas le lancer.
- Un commentaire est au présent et ne cite **jamais** un numéro de tâche, de spec ou de
  section. Les annotations « Review Focus » de ce plan sont des notes au constructeur, pas du
  texte à recopier.
- **Écritures Git** : l'agent n'en fait aucune (`docs/conventions/git.md`). Chaque étape
  « Commit » donne la commande au propriétaire, qui l'exécute. Un commit par tâche, aplati à
  la fusion, pour que le travail voyage entre deux machines.
- `packages/db` n'importe jamais `packages/domain`. Le dépôt reçoit des primitives, dont les
  dates de coupure calculées par le domaine.
- Assertions de refus : `rejects.toMatchObject({ message: CONST })`, jamais `toThrow`, qui
  compare par sous-chaîne. Côté actions, comparer `error.message === CONST`, jamais
  `includes`.
- Aucune constante d'erreur n'est une sous-chaîne d'une autre.
- Chaque server action et chaque route de pièce rappelle sa garde : une action est une route
  publique.
- Une valeur d'énumération ne s'affiche jamais brute : elle passe par une clé du catalogue.
- Une action qu'un rôle ne peut pas exercer n'est pas rendue grisée, elle n'est pas rendue.
- Les champs postés et dérivés d'un objet littéral se valident par `Object.hasOwn`, jamais
  par accès direct (`constructor`).
- Un `select` de motif ou de décision a un premier choix vide, refusé aussi côté serveur.
- Les seuils de couverture de `packages/domain`, de `packages/core` et de `packages/db` hors
  `src/repositories/**` restent à **100 %**.
- Avant d'écrire du code Next, lire le guide concerné dans `node_modules/next/dist/docs/` :
  le `AGENTS.md` des applications l'exige, l'API diffère de l'habitude.
- La suite d'intégration consomme `@clemperl/db` par `dist/src/` : rebâtir le paquet avant de
  la lancer, et vérifier une mutation dans `dist/src/`, pas dans la source.
- `revalidatePath` suit la structure de fichiers : `"/[locale]/orders/[reference]/dispute"`
  avec `"page"` dans la boutique, sans segment de locale dans le vendeur et l'administration.

## Review Focus

Les cinq entrées que la spec implique sans qu'aucune tâche ne les éprouve d'elle-même. Le
test qui fixe chacune est ajouté à la tâche qui porte le code.

1. **Un champ de fichier laissé vide.** Le navigateur poste alors un `File` de taille nulle
   et de nom vide. Il ne doit ni être stocké ni compter dans la limite de trois. Test en
   tâche 6, sur `submittedFiles`.
2. **Des pièces irrecevables** : quatre fichiers, un fichier de 6 Mo, un `.zip`. Le refus
   tombe AVANT tout téléversement, sans quoi chaque formulaire refusé laisse un orphelin
   dans le bucket. Tests en tâche 2 (règles) et en tâche 6 (aucun téléversement).
3. **Aucune ligne, ou une ligne d'une autre commande**, postée à la main. Refus nommé, et
   rien n'est écrit. Test en tâche 4.
4. **La frontière des délais.** Une commande expédiée il y a exactement quatorze jours est
   encore contestable, une milliseconde de plus ne l'est plus ; un litige silencieux depuis
   exactement sept jours est mûr, une milliseconde de moins ne l'est pas. Test en tâche 2.
5. **Un identifiant de pièce deviné** par un autre acheteur ou une autre boutique. Réponse
   404 et non 403 : répondre « interdit » confirmerait que la pièce existe. Tests en tâche 5
   (lectures portées) et dans chaque route (tâches 7, 8, 9).

```prisma
  DAMAGED
  WRONG_ITEM
  NOT_RECEIVED

  OPEN
  DECIDED_FOR_BUYER
  DECIDED_FOR_VENDOR
  SERVED

}

  BUYER
  VENDOR

  @@map("dispute_party")
}
```

| Modèle, table | Champs | Contraintes |
| --- | --- | --- |
| `Dispute`, `disputes` | `id`, `orderId`, `reason`, `status` (défaut `OPEN`), `locale`, `lastActivityAt`, `decisionComment?`, `decidedAt?`, `decidedById?`, `servedAt?`, `createdAt`, `updatedAt` | `orderId` unique ; `order` en `Cascade` ; `decidedBy User?` en `SetNull` ; index `[status, lastActivityAt]` |
| `DisputeItem`, `dispute_items` | `id`, `disputeId`, `orderItemId` | unique `[disputeId, orderItemId]` ; les deux relations en `Cascade` |
| `DisputeMessage`, `dispute_messages` | `id`, `disputeId`, `authorId?`, `party`, `body`, `createdAt` | `author User?` en `SetNull` (supprimer un compte ne doit pas effacer le fil) ; index `[disputeId, createdAt]` |
| `DisputeAttachment`, `dispute_attachments` | `id`, `messageId`, `objectPath`, `mimeType`, `sizeBytes`, `originalName`, `createdAt` | `message` en `Cascade` |

Les colonnes en `snake_case` par `@map`, et les tables au pluriel, comme toutes celles du
schéma. `Order` gagne `shippedAt DateTime? @map("shipped_at")` et `dispute Dispute?` ;
`OrderItem` et `User` gagnent les relations inverses que Prisma exige.

Commenter chaque choix qui n'est pas évident AVANT d'appliquer la migration : le `sha256` du
fichier est enregistré, et le modifier après fait diverger la somme. C'est un piège payé.

| Depuis | `SERVE` | `DECIDE_FOR_BUYER` | `DECIDE_FOR_VENDOR` |
| --- | --- | --- | --- |
| `OPEN` | `SERVED` | `DECIDED_FOR_BUYER` | `DECIDED_FOR_VENDOR` |
| `DECIDED_FOR_BUYER` | `SERVED` | | |
| `DECIDED_FOR_VENDOR` | | | |
| `SERVED` | | | |

La table dit quelles transitions existent, jamais qui les emprunte : l'acheteur seul sert,
l'administration seule tranche, chacun derrière sa garde.

Les validations cumulent leurs violations, comme `validateApplication` : une personne qui
corrige a besoin de la liste entière. Le récit et les messages se comparent après `trim()`.
Les pièces reprennent `ACCEPTED_MIME_TYPES` et `MAX_DOCUMENT_SIZE_BYTES` tels quels, jamais
une copie : la valeur est aussi le plafond du stockage.

  - `decideDispute(prisma, input: { disputeId: string; decidedById: string; from: string; status: string; comment: string }): Promise<{ orderId: string; reference: string; buyerEmail: string; buyerLocale: string; vendorContactEmail: string; vendorLocale: string }>`
  - `markDisputeServed(prisma, input: { buyerId: string; disputeId: string; from: string }): Promise<void>`

**`openDispute`**, dans une transaction :
1. relire la commande par `{ reference, buyerId }` : absente, `ERROR_ORDER_NOT_FOUND` ;
2. exiger `status: "SHIPPED"` et `shippedAt >= shippedAfter` : sinon `ERROR_DISPUTE_NOT_ELIGIBLE`.
   `shippedAfter` vient de `disputeOpeningCutoff`, calculé par l'appelant ;
3. exiger que `lineIds` soit non vide et inclus dans les lignes de la commande : sinon
   `ERROR_DISPUTE_INVALID_LINES` ;
4. créer le litige, ses lignes, le premier message (`party: "BUYER"`, `authorId: buyerId`)
   et ses pièces, `lastActivityAt` à maintenant. Une violation d'unicité sur `orderId` lève
   `ERROR_DISPUTE_EXISTS` : c'est la garde contre deux ouvertures simultanées ;
5. rendre l'adresse de contact de la boutique et sa langue,
   `vendor.application?.locale ?? "fr"`, comme `retireProduct`.

**Les deux messages** passent par une aide privée qui porte la portée, sur le modèle de
`writeOrderStatus` : `postDisputeMessageAsBuyer` filtre par `order: { buyerId }`,
`postDisputeMessageAsVendor` par `order: { vendorId }`, et l'aide n'est pas exportée. Dans
une transaction, un `updateMany` sur `{ id, status: "OPEN", order: portée }` avance
`lastActivityAt` ; un compte nul distingue `ERROR_DISPUTE_STALE` (le litige existe dans la
portée) de `ERROR_DISPUTE_NOT_FOUND`. Le message et ses pièces ne s'écrivent qu'ensuite.

**`decideDispute`** et **`markDisputeServed`** sont des comparaisons-et-échanges sur
`status: from`. La décision écrit `decisionComment`, `decidedAt`, `decidedById` ; servir
écrit `servedAt` et laisse les champs de décision intacts. `decideDispute` rend de quoi écrire
aux deux parties, lu dans la même transaction : l'adresse de l'acheteur, la langue du litige,
l'adresse et la langue de la boutique.
